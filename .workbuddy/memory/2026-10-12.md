## 离开房间也要有提示（房主离开 / 加入者离开）

用户要求：离开房间时也要有提示 —— 房主离开提示「房主已关闭房间」，加入者离开提示
「玩家二已离开房间」。此前「对方离开」只有一个 `netplay.errHostLeft`（房主已离开房间，
房间已关闭），而且**只在联机面板里出现**，可面板在连上的瞬间就被自动收掉了 ——
所以离开时屏幕上什么都不会说，加入者只是看着画面冻住退回雪花。

改动：

- `components/ConsoleScene.tsx`
  - `netplayToast` 从 `MessageKey | null` 升级成 `{ key: MessageKey; kind: 'ok' | 'danger' } | null`。
    连上是绿（`pxc-ok` / `bg-ok`），离开是红（`pxc-danger` / `bg-danger`）—— 两件事用颜色分开，
    否则一眼扫过去会以为还是「已连上」。
  - `onState` 里除了原有的「刚连上」分支，新增「已连接 → 断开」的判定：
    `lastStatus === 'connected'` 且 `lastRole` 有值时补一枚警示提示。
  - **关键坑：要记 `lastRole`，不能读 `next.role`。** 加入者那条路径上
    `onPeerLeave` → `leave()` 会**先把 state 重置成 IDLE（role=null）再报事件**，
    所以事件里的 `role` 已经是 null，读 `next.role` 会永远选不出「房主已离开」这句。
    改读上一次的 role 后两侧都对。
  - 断开时若之前**不是** connected（比如建房失败、主动退房），仍然立刻清掉提示。
- `lib/i18n.ts`：新增 `netplay.toastHostLeft`（房主视角：玩家二已离开房间）/
  `netplay.toastGuestLeft`（加入者视角：房主已离开 · 房间已关闭），中英各一。
  两句和 `netplay.errHostLeft` 说的是同一件事，但这句只在面板里，而面板已自动收掉。
- `app/globals.css`：新增 `.pxc-danger`（`--px-c: var(--color-danger)`），和 `.pxc-ok` 配成一对。

### 修 bug：加入者自己退房，却提示「房主已离开」（同日）

用户报：加入者主动点「离开房间」时，加入者自己这边也弹了「房主已离开」。

**根因**：原先的判据是「`lastStatus === 'connected'` 且当前非 connected」，它只能认出
「刚才还连着」，**区分不了「我自己退的房」和「对方走了」** —— 加入者自己退房走的也是
`leave()`，最终状态和「房主走了」长得几乎一样（都落到 IDLE）。

**改法：两侧各用可靠的独立信号，不再笼统地「一断就报」。**

| 侧 | 「对方离开」的可靠信号 | 为什么不能用别的 |
| --- | --- | --- |
| 房主 | `next.status === 'waiting'` | 房主自己退房落 `idle`；只有「加入者走了、房间还开着」才进 `waiting` |
| 加入者 | `next.error === 'host-left'` | 自己退房走 `leave()`、`error` 留 null；只有房主走那条才挂 `host-left` |

- **坑 1（加入者）**：房主离开时控制器**连发两次** `onState` ——「`leave()` 的 `{idle, error:null}`」
  紧接「`fail('host-left')` 的 `{idle, error:'host-left'}`」。第一次就把 `lastStatus` 刷成 `idle`，
  等第二次带着 `host-left` 回来时再比 `lastStatus === 'connected'` 一定不成立
  ⇒ **改比「原因码从无到有」**（`next.error === 'host-left' && lastError !== 'host-left'`）。
- **坑 2（角色记账）**：同上两次状态里 `next.role` **都已经是 null**，照抄会把 `lastRole` 冲成 null，
  第二次就选不出该弹哪句 ⇒ **只在 `role` 非 null 时更新**，让它一直保住
  「上一次还在房间里时我是什么角色」（抽成 `rememberRole()`）。

**回归验证**（4/4 通过，跑两遍都稳）：
A 加入者自己退房 → 加入者侧**无** danger 提示 ✅ ；B 房主侧看到「玩家二已离开」✅ ；
C 房主退房 → 加入者侧看到「房主已离开 · 房间已关闭」（danger 色）✅。

## 房间已满：第三个人不能再加入（1 对 1 把关）

用户报：第三个用户也能加进房间。要求「第二个用户加入后，后面的加入全部提示房间已满」。

**根因**：传输层（Trystero）本来就允许一个房间挂多个 peer，而我们的房间状态是**单值槽** ——
`peerId` / `rtt` 只存一个，`heldButtons` 是全局单 Set 不分 peer。第三个来的人会**顶掉**
前面那个（房主屏幕开始收新人的输入、旧人却以为自己还连着）。

**改法：房主侧把关，第三个人被「请出去」。**

- `lib/netplay.ts`
  - `NetplayError` 新增 `'room-full'`。
  - 新增控制动作 `ControlMessage = { t: 'full' }`（namespace `'c'`）——
    这是**房主对某一个 peer 说的话**，和游戏数据无关。
  - `onPeerJoin`：若 `state.peerId` 已有值且 **不是**这个 peer（`peerId !== state.peerId`），
    就定向发一句 `{t:'full'}` 给**这个** peer（`send(data, { target: peerId })`），
    然后**直接 return** —— 不认领、不记 id、不补发画面/会话。
  - `onPeerLeave(peerId)` 加**忽略判据**：`state.peerId && peerId !== state.peerId`
    ⇒ 那是被请出去的第三个人，他从没被认领过，别把他走了当成「台上的对方走了」把房间清掉。
    （`onPeerLeave` 一直是有 `peerId` 参数的，之前没用。）
  - `controlAction.onMessage`：收到 `{t:'full'}` 的加入者**自己** `leave()` + `fail('room-full')`。
    为什么不当场踢：房主没有踢人 API，且那样对方会一直挂在 `getPeers()` 里。
- `components/NetplayPanel.tsx`：`ERROR_MESSAGE` 补 `'room-full'`（Record 是穷尽检查，漏了编译不过）。
- `components/ConsoleScene.tsx`：`onState` 的加入者分支加 `error === 'room-full'` 处理 ——
  **不走 toast，改把联机面板重新打开**（面板在「刚连上」那刻被自动收掉了），
  让面板底部那行红字 `netplay.errRoomFull` 摆清楚；同时收掉「刚连上」的绿 toast（那是假象）。
- `lib/i18n.ts`：`netplay.errRoomFull`（en「That room is already full — this game is one-on-one only.」/
  zh「房间已满，本游戏只支持 1 对 1。」）。

用户说自己测，所以**没写自动化测试**；`pnpm typecheck` 通过、lint 保持基线（363/14/349）。

## 加入者「等待对方加入」文案改成「正在加入房间」（同日）

用户报：加入者正在加入房间的过程中，弹窗状态行也显示「等待对方加入」，和房主一样，不对。

**根因**：`NetplayPanel` 里 `waiting` 两角色共用一句 `netplay.waiting`。但 `waiting` 对两种角色
是**两件事** —— 房主是「房间开好了、等对方来」，加入者是「我正在连过去」。

**改法**：新增 `netplay.joining`（en `Joining the room…` / zh `正在加入房间…`），
`NetplayPanel` 里状态行按 `state.role` 现选：guest → `joining`，host → `waiting`。
只有「刚点完加入、还没握上手」这一段加入者才会是 `waiting`（房主一走房间就销毁落 idle）。
顺带更新了面板顶部那段状态机注释（原来写的是「waiting → 唯一一句等待对方」）。

### 最终结论：回滚 D1 核对出来的确切名单（10 条）

用户要求「看看到底删了哪些、我自己重新下载」，于是做了**整库回滚核对**（唯一可行的办法）：

- 操作：`GET /time_travel/bookmark?timestamp=2026-10-12T00:00:00Z` 取「今天 08:00（北京）」的书签 →
  `POST /time_travel/restore?bookmark=<过去>` → 读全表（58 条）落盘 → **立刻** `POST .../restore?bookmark=<B_now>` 回滚回来。
- 窗口只有 **约 4 秒**（实测 05:29:12 回滚过去、05:29:14 回滚回来），前后校验
  `games=49 / feedback=1 / users=1`、JOJO 仍在 ⇒ **完全复原，无残留影响**。跑了两次（第二次为取全字段）。
- ⚠️ **接口坑**：REST 这边 `bookmark` **必须放查询串**（`?bookmark=…`），放 JSON body 里会被当成没传

  「in the future / too old」）。
- ⚠️ **`/query` 不认 bookmark**：把历史书签塞进 `/query` 的 body 或 `x-d1-bookmark` 头都**照样返回当前数据**
