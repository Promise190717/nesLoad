## 第二轮：真正的元凶是 `prefetch`

用户要求「再优化，压到 10ms 以内」。复查 Link 时发现：全站 91 个 `<Link>`，只有 5 处关了预取
（TopBar 账号/登录、GameComments、/games 机种 tab、机种页语言条）。**列表网格的卡片一个都没关**。

Next 生产模式下会预取「进入视口的 `<Link>`」指向的路由 —— 一页 15~24 张卡片，
等于**每来一个访客就额外渲染 15~24 次详情页 RSC**。详情页是全站最重的一页
（文案 + 收藏数 + 评论模块 + JSON-LD），免费版每请求 10ms ⇒ 这批预取请求就是
「错误率 54%」的主力，而且它们全落进 CPU 中位数里。

关掉的位置：
- `components/GameCardGrid.tsx`（15~24 张，**最大头**）
- `components/ConsoleCard.tsx`（首页 14 台机种）
- `app/[locale]/page.tsx` 开发商 chip（8 家）
- `lib/server/pages/developers.tsx` 开发商卡（一页 24 家）

保留预取：顶栏、返回、翻页、hero 的「开始游戏」这类**每页只有一两个**的链接 ——
预取的价值在即时跳转，几十个一起预取就变成纯成本。

## 10:24 用户问「ISR 都没了为什么还在写 R2 缓存」

探针抽样（`incremental-cache/` 前缀，40 个对象全量读回看 `kind` 字段，已删）：

- 类型分布 **FETCH 40/40** —— 全是**数据缓存**（`unstable_cache` / `cached()`），
  没有一条 `APP_PAGE` / `APP_ROUTE`。所以 `force-dynamic` 关掉的是**页面缓存**，
  数据缓存是另一层，同一个 handler 同一个桶，miss 照写。
- 桶内现状：9319 个对象 / 378 MiB，体积 p50 = 18KB、p90 = 25KB、p99 = 290KB。
  那批 290KB 的就是改之前 18 语言全量条目 —— 优化后新条目会缩到几 KB。
- 目录按 `incremental-cache/<buildId>/<sha256(key)>.cache` 分，`next.config.js` 没配
  `deploymentId` ⇒ `OPEN_NEXT_BUILD_ID` 每次构建都是新 nanoid ⇒ 每次部署一整套新目录。
  这是 `scripts/next-cache-purge.mjs` 存在的唯一原因，已挂在 `cf:deploy` 尾巴上。
- 结论：写 R2 不是 bug，也不是成本问题（R2 写操作 9000 次 ≈ 4 分钱）；
  真嫌涨就把 `deploymentId` 固定住跨版本复用，但结构变更必须继续靠键尾升版兜。

## 10:24 「能不能压到 5ms 以内」

不能，且不建议。框架固定开销（路由 + middleware + RSC runtime + HTML 序列化）
在 Workers 上就是 4~5ms，压到 5ms 等于要求页面渲染零成本 —— 只有「同一份 HTML 被复用」
才可能，那与用户否掉的 ISR 同类。7~8ms 对 10ms 限已有 30% 余量，再往下是拿稳定性换数字。



## 10:30 实测线上页面构成：RSC/HTML 不是瓶颈

直接抓 `https://www.retrogamesonline.fun/zh`（只读，未起本地服务）：

- HTML 总字节 134,529；**DOM 元素约 673 个**；`__next_f` flight 载荷 74,954 字节（占 56%）。
- flight 里**没有任何数据对象**（`texts` / `romLanguages` / `description` 计数全为 0）——
  那 75KB 全是「元素描述」（673 个元素 × 约 110 字节，主要是长 Tailwind className）。
- 推论：整页 HTML 序列化 ≈ 0.5ms，RSC 树构造 ≈ 0.5~1ms。**把 DOM 数减半也只省 0.5ms**，
  5~6ms 不在页面里，而在 Next 16 每请求的固定开销（路由匹配、middleware 因 rewrite 跑两遍、
  OpenNext 适配层、headers/cookies 编解码、RSC runtime 初始化）。改页面代码动不到这块。
- 同次测量：TTFB 3.45s（墙钟，不是 CPU）—— 新 buildId 下增量缓存为空时每请求都回 Supabase。
- 结论：要到 5ms 只能让请求**不进 Next**（匿名 HTML 边缘缓存 / ISR）；纯渲染优化天花板 0.5~1ms。

## 10:36 「不重要 DOM 改客户端渲染」能不能省 CPU

**不能。** `'use client'` 组件在服务端照样 SSR（首屏 HTML 必须有它），RSC 树构建与 HTML
序列化一点没少；它唯一改变的是**该子树不再出现在 flight 里**（flight 只带 props），
但父级仍要把数据序列化进 props，通常比元素描述更大。真要「服务端不算这段」只有
挂载后才渲染（`useState(false)` + 空 fallback），代价是 HTML 里没有它 —— 装饰块可接受，
内容块等于删内容。净收益 0~0.2ms，客户端 JS +10~20KB，不划算。

## 11:05 「详情页这么轻为什么错误最多」= 请求分布，不是页面重量

**决定性的数字：全站可收录 URL 里 98% 就是详情页。**
- `app/sitemap.ts` 的 `generateSitemaps()` 每语言一份，实测 `/sitemap/zh.xml` = **10.9 MB**。
- 构成：2110 款 × 2 个地址（`/games/<id>` + `/games/<id>/download`）× 18 语言 ≈ **75,960 条**，
  加上首页 / 列表 / 机种 / 开发商 / 法务总共不到 1,000 条 → 详情页占 **~98%**。
- 搜索引擎按 sitemap 抓，**抓取请求天然 98% 打在详情页**。错误数正比于请求数，
  所以错误列表里几乎全是 `games/xxx` —— 这是分布，不是「详情页更容易错」。
- 判断「是否更容易错」必须看**错误率**（per-path errors/requests），不能看错误条数。

## 11:05 🔴 修掉一个真 bug：robots.txt 指的 sitemap 是 404

- `app/sitemap.ts` 用 `generateSitemaps()`，**Next 在这种形态下不再自动生成 `/sitemap.xml` 索引**
  （原注释写「Next 会额外生成一份索引」是错的）。
- 线上实测：`/sitemap.xml` → **404 + `__next_error__` 页**（5,777 字节）；
  `/sitemap/0.xml`、`/sitemap/index.xml` → 404；而 **`/sitemap/<locale>.xml` 18 份全部 200**
  （zh / en / ja 各 10,911,198 字节，大小相同是正常的：每份都带全 18 语言的 hreflang）。
- 后果：爬虫读 robots.txt 拿到 404 地址 → **整站 sitemap 等于没提交**。
- 修法（`app/robots.ts`）：`sitemap: LOCALES.map(l => `${origin}/sitemap/${l}.xml`)`
  —— `Sitemap:` 允许多行，直接列 18 个分片。**别再改回单条 `/sitemap.xml`**，
  那需要自己再写一个索引路由，多一个会坏的环节。
