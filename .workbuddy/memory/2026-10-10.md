### 排查：联机玩街机「有时像慢动作」（用户报的，尚未改代码）

用户和朋友联机玩街机时偶发卡顿、像慢动作，问单人会不会这样。
翻了代码 + 判断如下，**记下来免得下次重新推**：

- 慢动作（平滑地变慢）而不是跳帧 / 冻帧，指向**房主主循环掉到 60 fps 以下**。
  RetroArch 的 emscripten 主循环是 rAF + vsync 驱动的：一帧超 16.7 ms，它就整体跑慢，
  **不跳帧** —— 这也解释了为什么是「慢动作」而不是「一顿一顿」。
- 加入者那侧**不背这个锅**：`RemoteScreen` 只是一条 `<video>`，没有模拟器。
  他卡就是网络 / 解码，表现应是**跳帧、冻结、花屏**，不是平滑慢放。
- 房主每帧的额外开销（都是 2026-10-08 那套「房主出画面」架构带来的）：
  `canvas.captureStream(60)`（`ConsoleScene` 的 `CAPTURE_FPS`）、VP8/VP9 编码
  （画布后备存储是 720×dpr，即 900×675）、`audio-tap` 旁路出来的音频 + Opus 编码。
- 「有时候」+「只在街机」：FBNeo 是三个核心里最重的，再叠加编码就容易破预算。
- 另一个怀疑点：`audio-tap` 往图里多接一路 `MediaStreamAudioDestinationNode` 之后，
  若核心是按音频时钟配速的，音频线程被拖慢也会把画面拖成慢动作 —— 和上一条指向同一个结论。

**判别法**（给用户的）：同一盘街机单独玩一段，不出现 = 就是联机的编码开销；
联机时看面板上的 rtt，rtt 低但画面慢 = CPU，rtt 高且跳帧 = 网络。

> ⚠️ 上面那条「Trystero 不暴露 `RTCPeerConnection`，改不了码率」**是错的，已推翻**：
> `room.getPeers()` 就返回 `Record<string, RTCPeerConnection>`（types.d.mts:157），
> 从 `getSenders()` 能按 track 反查回 `RTCRtpSender` 并 `setParameters`。
> 只是 `room.addStream()` 本身在 0.26 里改成返回 `Promise<void>[]` 了，不再给 sender。

## 2026-10-10 「点第二款游戏后整个游戏区域变大」= 屏幕尺寸被判定成由 canvas 撑

**症状**：插第一盘正常，**换第二盘时整台电视机（整个游戏区域）大一圈**，而且一盘比一盘大。

**复现与定位**（用 `chrome --headless --force-device-scale-factor=1.25` + CDP 驱动真实页面，
`DOM.setFileInputFiles` 插自造的最小 iNES ROM 两次）：

- eb87505 把屏幕 div 的 `h-[540px] w-[720px]` 删了（同一次还把屏幕的 `m-[15px]` 挪成内圈的
  `m-[8px] mx-2.5`），于是**屏幕变成由 canvas 的固有尺寸决定**——canvas 是 .screen 里唯一在流里的孩子。
- canvas 的尺寸会被三方轮番改：① 核心启动时先 `canvas.width=64` 探一下，发现「CSS 没锁死尺寸」
  就把探之前的 clientWidth **写死回内联样式**（日志 `[WARN] Canvas size should be set using CSS properties!`）；
  ② 核心随后按 `devicePixelRatio` 把后备存储设成 720×dpr（`_emscripten_set_canvas_element_size`，
  125% = 900×675）；③ Nostalgist 每次 launch 都往 canvas 写一次 `width/height:100%`。
- 于是每次 launch：Nostalgist 把 CSS 复位成 100% → .screen 跟着 canvas 的**属性**变成 900 →
  核心把探到的 clientWidth 900 写死 → 机身 720→900→1125…**每换一盘乘一次 dpr**。
  100% 缩放的机器上永远看不出来，125%/150% 上必现（实测 T1=720×540、T2=900×675、T3=1125×844）。
- 2026-10-10 的 `size: {width: canvas.width, height: canvas.height}` 也在**读回那个脏值**，
  把上一次的后备存储尺寸烤进这一次 launch（trace 里能看到 `Module.setCanvasSize(900,675)`）。

**修法**（已验证：dpr 1.25 下连插三盘，屏幕恒为 720×540，核心那句 WARN 消失，
后备存储仍是 900×675 = 清晰度不受影响）：

1. `components/RetroTv.tsx`：屏幕 div 恢复 `h-[540px] w-[720px]`（注释写清为什么不能省）。
2. `lib/emulator.ts`：新增 `SCREEN_WIDTH/SCREEN_HEIGHT = 720/540`；launch 的 `size`
   改成写死这两个常量，不再读 `canvas.width/height`；RetroTv 的 canvas 属性也改用它们。

**顺带发现（未改，等用户定）**：机身实际是 **740**（720 + 内圈左右外边距 10×2），不是文档里的
766（那是屏幕自己还带 15px 外边距时的数字）。globals.css / i18n 的 `notice.desktopOnly` /
README 里的 766 都是旧数，`TV_WIDTH` 已同步改成 740 并在注释里标了这件事。
900px 断点不用动（788 < 900，余量还在）。

## 手柄支持排查（用户问「看下现在这个支持手柄么」）

**结论：引擎层支持，应用层零支持。**

- 引擎层**支持**，而且不用配：`[INFO] [Input] Found joypad driver: "rwebpad"`、
  `[Input] Found input driver: "rwebinput"`（把 RetroArch 的 `log_verbosity` 临时打开才看到），
  插着的浏览器手柄会被 autoconfig：`[INFO] [Autoconf] … STANDARD GAMEPAD … configured in port 1.`
  → **手柄落在 1P**，和键盘的 1P 并存。
- **实测过它真能驱动游戏**：造了一盘「A 按住时画面恒黑」的 NES ROM，再用 CDP 篡改
  `navigator.getGamepads` 喂一个假手柄。只改这个 JS 变量（不产生任何 DOM 事件），
  游戏画面就稳定切到另一个状态 —— 页面里除 Emscripten 之外没有别的消费者，所以「引擎
  在读浏览器 Gamepad API 并喂给游戏」这条是硬结论。
- **应用层完全没碰**：`lib/` 和 `components/` 里 `gamepad` 关键字 0 处。键位面板只配键盘、
  没有「手柄已连接」提示、页脚按键说明只有键盘。手柄能用纯粹是核心默认行为，用户既看不到
  也改不了（改键、换键位都做不到）。
- **联机里加入者的手柄完全无效**（且是设计使然）：转发链路是
  `物理键盘 code --codeToButton(bindings.p1)--> 钮名 --> sendButton`，只认 DOM 键盘事件。
  加入者本机没有模拟器，手柄按下去没有任何东西读它。房主自己的手柄能用（就是他本机的 1P）。
- 未实测：两个手柄能不能自动分到 1P/2P（autoconfig 是「按顺序占端口」，大概率可以，但没验）。

### 排查手法（下次还这么干，别再走弯路）

1. **无头 Chrome 观察不到输入的效果**：`--headless=new` 下 rAF 基本不跑（`Page.startScreencast`
   投帧也不驱动它），模拟器实际是停摆的 —— 于是「按住键画面不变」全是假象。
   要观测必须用**离屏真窗口**：
   `--window-position=-3000,-3000 --disable-backgrounding-occluded-windows
   --disable-renderer-backgrounding --disable-features=CalculateNativeWinOcclusion,IntensiveWakeUpThrottling`
   并在导航后调 `Page.bringToFront`。
2. **同时开多个 Chrome 实例会互相抢渲染**：只有前台那个能跑满帧，其余全被节流 ——
   表现为「这次测什么都是冻住的」。测之前先把自己起的实例杀干净
   （按命令行里的 `remote-debugging-port=92` / 独立 `--user-data-dir` 过滤，**别动用户的 Chrome**）。
3. **判据别用颜色，用「画面是否变化」**：`.crt` 叠加层 + 这个核心的调色板映射
   （`$3F00` 写什么颜色、出来是什么颜色）都对不上直觉，肉眼/取色都会被带偏；
   把 ROM 写成「无输入时持续变色，输入按下时恒定」再比连拍哈希/主色才靠谱。
   **采样间隔要不等距**，否则会和变色周期锁相，出现「4 张全一样」的假冻结。
4. **临时打开 RetroArch 详细日志**是拿到 `rwebpad` / autoconfig 证据的关键：
   在 `retroarchConfig` 里临时加 `log_verbosity: 'true'`（它让 `tsc` 报错，验完必须删）。
