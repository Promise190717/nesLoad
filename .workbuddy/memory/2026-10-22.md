## 线上 1102「Worker exceeded CPU time limit」定位与处置

**结论：免费版 Workers 每请求 CPU 硬限 10ms（不可配置，`limits.cpu_ms` 只对付费版生效）。
Next SSR 一次渲染是几十到几百 ms，所以只要请求真的进入渲染就必炸；命中增量缓存时
`enableCacheInterception` 在初始化渲染器前返回，CPU 几 ms，就正常。**
用户报「同一个页面有时正常有时 1102」= 冷/热差别，不是页面坏了。

日志证据（用户提供）：失败集中在非默认语言长尾页与 `/download`
（`/zh-TW/games/tales-of-destiny-ii`、`/vi/games/away-shuffle-dungeon/download?lang=en`），
同期 `/games/weaponlord` 正常 ⇒ 爬虫按 sitemap 扫 18 语言 × 7.6 万条，持续制造冷渲染。

**根因：详情页 / 下载页只写了 `revalidate`，没有 `generateStaticParams`。**
Next 不知道要提前生成哪些 `[id]`，全部退化成 on-demand ISR，线上首访必须现场 SSR。
（这条同时推翻了两处旧认知：① `/download` 页头的「读 cookie 语言所以动态渲染」已过时，
`readLocaleParam` 只读 params；② 详情页链路上 GamesShell / locale 布局都不读 cookie/headers，
天然可静态，`resolveSiteOrigin` 用的是 `SITE_URL` 而不是请求 host。）

### 已改

`app/[locale]/games/[id]/page.tsx`、`app/[locale]/games/[id]/download/page.tsx`
各加一个 `generateStaticParams()`：返回 `DEFAULT_LOCALE` 的全部 slug（`listGameStubs()`）。
`cf:build` 时渲染好 → `opennextjs-cloudflare deploy` 的 `populateCache` 上传 R2 →
运行时命中缓存，不再现场渲染。读库失败返回 `[]` 退化成 on-demand，不让构建挂掉。
typecheck / lint 均过。**未实测、未构建**（用户要求不主动测试）。

### 待用户决定

1. **构建成本**：2110 款 × 2 页 ≈ 4200 页预渲染，`cf:build` 时间会明显上涨，
   且构建环境必须能连 Supabase（`SUPABASE_URL` + `SUPABASE_SECRET_KEY`），否则静默退回。
2. **sitemap 收缩**：`app/sitemap.ts` 现在每语言一份、18 份共 7.6 万条。只列
   en/zh/ja/ko 能把爬虫制造的冷渲染砍掉 ~78%，是免费版最直接的一刀，但属 SEO 决策。
3. 其余 17 种语言仍是 on-demand，冷请求依旧会偶发 1102 ——
   **免费版 10ms 对 Next SSR 是硬墙，预渲染只能把「经常」压成「偶发」，不能归零。**
   要零故障只有「$5/月 Workers Paid」或「全站改纯静态分发」。

## 16:00 更正：nostalgist 原生支持按需换碟，但每碟只能一个文件

**上面那条「EJS 同步切碟所以只能全量」是错的，作废。** 读 `node_modules/nostalgist/dist/nostalgist.js`：

- `updateRom()`：`multiDisc = firstFile.name.endsWith('.m3u')`；m3u 模式下 `rom[1]` 立即
  创建（当前碟），`rom[2..]` 存进 `multiDiscRom` Map **等换碟时才写**。
- `switchDisc(index)`：取 Map 里那一项 → `fs.writeFile` 写进内容目录 → 发
  `DISK_EJECT_TOGGLE` + `DISK_NEXT/PREV` → 更新 `multiDiscIndex`。启动时
  `if (multiDisc) multiDiscIndex = 1`（所以 `switchDisc(2)` 的 delta 正确）。
- **`index` 是 rom 数组下标**（m3u=0、第一碟=1、第二碟=2），不是「第几张碟」，
  但第 N 张碟正好传 N。`Controller.switchDisc` 就是转给它。

🔴 **硬约束**：m3u 模式下**一个数组项 = 一张碟**。zip 里是 cue + bin 两个文件，
塞进数组会被当成两张碟、bin 永远不会被写进 FS。所以：

- **chd / pbp 多碟**（24 行，12 组）→ 走 m3u，可换碟 ✓
- **zip / 7z 多碟**（78 行，36 组）→ 不能走 m3u，**只加载第一碟**（退化为单碟）

## 傍晚：/play UI 优化（小屏布局是主因）

用户原话「play 页面的 ui 现在太丑了，特别是小屏幕下丑的过分」。

  `80dvh` 那套删除（`--play-display-height` 从此没人消费，注释已标注）。

  黑屏没有任何边界）。

  `play-navigation` 间距收紧。

## 18:05 Vercel 回源上游被拦 → 加「上行出口」ROM_EGRESS_ORIGIN

- 现象：同一份上游 ROM（例 `ace-combat-3`），Workers 上取得到、Vercel 上 502；
  用户确认**被拦的是 Vercel → 上游（retrogamesnexus.com）那一跳**。
- 结论：**不是代码问题**。上游前置 Cloudflare，风控按出口判：Worker 出口是 CF 自己的
  网段（同一张网的下一跳），Vercel 函数在 AWS 上（机房 IP + 非浏览器 TLS 指纹）
  → 挑战 / 403。伪造 UA 治不了（TLS 指纹对不上），别往那个方向使劲。
- 落地：`app/api/games/[id]/rom/route.ts` 加 `fetchThroughEgress()` —— 配了
  `ROM_EGRESS_ORIGIN` 就把**上游那批** ROM 改成请 CF 上那份站点的同一接口代取
  （`?lang/?disc/Range/If-Range` 原样转发，带 `x-nl-rom-egress` 防循环），
  本函数只转发响应（`relayEgress()` 只留 9 个头）。出口挂了退回直连。
  R2 自持那批不走这一跳。Vercel 上要设 `ROM_EGRESS_ORIGIN=https://www.retrogamesonline.fun`。
- 没选 `workers/rom-proxy`：它不认 `?lang=` / `?disc=`（只按 id 取默认那份），
  多语言 / 多碟会拿错文件。
- 治本仍是把 gba/nds/ps1 也搬进 R2（`scripts/migrate-roms-to-r2.mjs`）。
- 待用户验证：tsc + eslint 干净，未实测。
