# 2026-10-22

## 线上 1102「Worker exceeded CPU time limit」定位与处置

**结论：免费版 Workers 每请求 CPU 硬限 10ms（不可配置，`limits.cpu_ms` 只对付费版生效）。
Next SSR 一次渲染是几十到几百 ms，所以只要请求真的进入渲染就必炸；命中增量缓存时
`enableCacheInterception` 在初始化渲染器前返回，CPU 几 ms，就正常。**
用户报「同一个页面有时正常有时 1102」= 冷/热差别，不是页面坏了。

日志证据（用户提供）：失败集中在非默认语言长尾页与 `/download`
（`/zh-TW/games/tales-of-destiny-ii`、`/vi/games/away-shuffle-dungeon/download?lang=en`），
同期 `/games/weaponlord` 正常 ⇒ 爬虫按 sitemap 扫 18 语言 × 7.6 万条，持续制造冷渲染。

**根因：详情页 / 下载页只写了 `revalidate`，没有 `generateStaticParams`。**
Next 不知道要提前生成哪些 `[id]`，全部退化成 on-demand ISR，线上首访必须现场 SSR。
（这条同时推翻了两处旧认知：① `/download` 页头的「读 cookie 语言所以动态渲染」已过时，
`readLocaleParam` 只读 params；② 详情页链路上 GamesShell / locale 布局都不读 cookie/headers，
天然可静态，`resolveSiteOrigin` 用的是 `SITE_URL` 而不是请求 host。）

### 已改

`app/[locale]/games/[id]/page.tsx`、`app/[locale]/games/[id]/download/page.tsx`
各加一个 `generateStaticParams()`：返回 `DEFAULT_LOCALE` 的全部 slug（`listGameStubs()`）。
`cf:build` 时渲染好 → `opennextjs-cloudflare deploy` 的 `populateCache` 上传 R2 →
运行时命中缓存，不再现场渲染。读库失败返回 `[]` 退化成 on-demand，不让构建挂掉。
typecheck / lint 均过。**未实测、未构建**（用户要求不主动测试）。

### 待用户决定

1. **构建成本**：2110 款 × 2 页 ≈ 4200 页预渲染，`cf:build` 时间会明显上涨，
   且构建环境必须能连 Supabase（`SUPABASE_URL` + `SUPABASE_SECRET_KEY`），否则静默退回。
2. **sitemap 收缩**：`app/sitemap.ts` 现在每语言一份、18 份共 7.6 万条。只列
   en/zh/ja/ko 能把爬虫制造的冷渲染砍掉 ~78%，是免费版最直接的一刀，但属 SEO 决策。
3. 其余 17 种语言仍是 on-demand，冷请求依旧会偶发 1102 ——
   **免费版 10ms 对 Next SSR 是硬墙，预渲染只能把「经常」压成「偶发」，不能归零。**
   要零故障只有「$5/月 Workers Paid」或「全站改纯静态分发」。
