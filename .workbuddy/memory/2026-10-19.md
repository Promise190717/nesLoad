## 线上 PS1 几乎全部打不开：根因是 ROM 代理传不了大文件（2026-10-19 定位）

- 现象：`/zh/consoles/ps1` 的 460 款里基本都开不了。
- 复现（本机 Chrome 无头 + 线上真实 `/zh/play?id=`）：296MB 的 `disney-tarzan.chd` 到手只有 **7,900,864 字节** ⇒ `checkChdIntegrity` 判 `truncated` ⇒ `载入失败: IncompleteRomError`。小文件（25MB `captain-tsubasa.pbp`）能正常起核。
- 直接量 `/api/games/<id>/rom`：整包 GET 反复只给 **1–3MB**（`http=200`，chunked，无 `Content-Length`）；`Range: bytes=0-4999999` 直接 **503 `error code: 1102`**（Worker 超资源上限）；但 1/2/4/8/16MB 的单段 Range 全部完整、且 **4 路并行 8MB 分片 19s 走完 32MB**。
- 上游 `files.retrogamesnexus.com` 直连同一文件 **296MB/383MB 全量正常**（2.5–4MB/s）⇒ 问题不在上游、不在 R2、不在核心/格式（`pcsx_rearmed` wasm 里有 `bin|cue|img|mdf|pbp|toc|cbn|m3u|chd|iso|exe`，BIOS 可回落 HLE）。
- 数据形状：PS1 460 款 = zip 245 / chd 131 / 7z 57 / pbp 22 / bin 2 / iso 2 / cnd 1（`cnd` 是错扩展名），全部 `files:` 走上游代理；抽样 12 个 chd 结构自检全 `ok`，**不是坏盘**。
- 结论：Cloudflare Worker 单请求搬不动 100MB+（约 50–60s / 100MB 量级的天花板），PS1 盘天生 200–780MB ⇒ 必然挂。同一条路 65MB 的 NDS 能过（44s），111MB 的直接 1102。

## 分片下载改「自适应档位」（`lib/http.ts` 第二次迭代）

用户看 Network 面板发现每次大小从几十 KB 到几千 KB 不等 —— 那是「固定 8 MiB + 失败对半切 + 重试」三层叠出来的。改成：

- 网格 `ROM_GRID_BYTES = 2 MiB`，档位按**格数**升降（4 格 8 MiB / 2 格 4 MiB / 1 格 2 MiB），`parts` 按格下标 —— 片大小可升降而拼装顺序不变。
- `ROM_DOWNGRADE_AFTER = 1`：一批切过就降一档（原来是硬试 8 MiB 4 次）；`ROM_UPGRADE_AFTER = 8` 干净 8 批才升回。
- `ROM_RETRY_FULL_BELOW = 4 MiB`：**大段只重试 1 次就切半**（切半比退避更有效），小块才用满 `ROM_SPAN_RETRIES = 3`。
- 段级再兜一层：一批彻底失败 → 歇 3 秒**原样重走一遍**（`worker` 里），第二遍内部照样重试/降档/切半。
- `spanBackoffMs` 封顶 2s → **5s**：实测 503 是**成片**来的（`41943040-50331647` 与 `50331648-58720255` 相邻段一起挂），是限流窗口，300ms 重撞没意义。
- `ROM_SPLIT_DEPTH` 一度被我改成 2 —— **错的**：8 MiB 段只切到 2 MiB 就到底了，比原来（切到 512 KiB）弱 4 倍，已改回 4。

自测：
- mock（`Response` + 固定种子模拟 503/截断）40 MiB：**逐字节一致**，7 个请求（理论 6）。
- 线上 92 MB pbp：65.5s 全量、头 `00504250`（PBP）✅；同日三次分别 167s / 79.8s / 65.5s，波动很大。
- 线上 296 MB chd：**连测三次都失败**（73% / 87% / 更低），失败点全是成片的 503。判断是我自己连续压测触发了**限流**（越测越差），不是逻辑问题 —— 但结论要写清：300 MB 级在这条路上仍然不稳，终极解仍是 R2。

- 排查结论：客户端原来只区分「fetch 抛错」和「成功」，非 2xx 一律算 `cloudFailed`；服务端这条链上最可能是 **401**（没登录 / 会话过期 / 被删号，`assertUser` 见 `lib/server/app-guard.ts`）—— 那种情况登录后自愈，和真正的同步故障是两件事。其它可能：`getGame` 404（游戏下架）、R2 写入抛错（500 `save-failed`，多半是 R2 四个变量之一丢了）。
- 改动（`components/PlaySaveControls.tsx`）：
  - 非 `ok` 时把 `status` + 响应体前 200 字打到控制台（`[nesload] 云端存档上传失败`），别再靠猜。
  - `401` → `setCloudAuthed(false)` + 新状态 `saveNoLogin`（warn 色），不再冒充「同步失败」。
  - 新词条 `play.saveNoLogin`：「未登录，未上云」/ `Sign in to sync` / `ログインで同期` / `로그인 후 동기화`（四语言；标签格半栏宽，文案压在 ~6 字内）。
- 没动的：`403`（封禁）仍算 `cloudFailed`；服务端逻辑一行没改（这条链看着没问题，真要复现得看线上日志）。

## 《豪血寺一族2》(/play?id=91436796…) 载入失败：romset 版本对不上

- 用户报线上 `zh/play?id=91436796-9182-4a3f-bbf7-ea089fc88216&mode=solo` 载入失败。
- 排查路径：接口拿到 `romName=pwrinst2.zip` / `consoleType=arcade` → 下 ROM（15,137,352 字节，zip 完好，分片重组 sha256 与整包一致，排除下载问题）→ 线上 `/cores/fbneo_libretro.wasm.gz` 200、`arcade-romsets.json` 200（带 `Range` 头会 404，是先前的误判）→ 核心里 `pwrinst2`/`g02.u42…` 都在，驱动确实编进去了。
- **真因**：zip 里程序 rom 是 `g02.u42/u43/u44/u45`（CRC a0b4ee99/178e3d24/8f6f6637/7b33bc43），那是 **`pwrinst2a`** 那一版；FBNeo 的 `pwrinst2` 驱动要的是 `g02.u42a…u45a`（ddfff811/5561f620/c4fd5d62/56279c1c）。而 `arcade-romsets.json` **只覆盖 CPS1**，Cave 这套只能靠文件名认驱动 ⇒ 原样把 `pwrinst2.zip` 交给核心 ⇒ 驱动查不到、静默失败。
- 修法（`lib/arcade-core.ts`）：新增 `EXTRA_DRIVERS`（`CoreTable`），把 `pwrinst2a` 的 20 条必需 rom 按 FBNeo `d_pwrinst2.cpp` 抄进来，`loadTables()` 合并到 `fbneo` 那张表。核心认出来后 **把名字换成 `pwrinst2a.zip`** 交过去 —— R2 里那份文件不用动、名字也不用改。`loadTables()` 返回类型从 `Tables | null` 收成 `Tables`（JSON 拉不到也照样返回「只有补丁」的表）。
- 校验：拿真实 zip 跑了一遍匹配逻辑（Python 复刻 `hasAllCrc`/`countNameHits`/`rank`）→ 命中 `fbneo / pwrinst2a`，20/20 名字全对（走 `namedRight` 那条，不重打包），表里没有别的驱动会撞。代码里那 20 条和 FBNeo 源码逐条 diff 一致。typecheck 只剩 open-next 4 条，eslint 0 条。未实测。
- ⚠️ 以后再遇到「街机静默失败」，先按同样套路比 CRC：拉 `d_<驱动>.cpp` 的 `xxxRomDesc[]` 对着 zip 中央目录看，名字像但 CRC 不同就是版本对不上。

## 排查：dev 报 `Jest worker encountered 2 child process exceptions`

- 现象：`next dev` 打不开页面，日志 `⨯ Failed to generate static paths for /[locale]:` + `Error: Jest worker encountered 2 child process exceptions, exceeding retry limit`，`/zh` 一直 500。
- 结论：**不是代码问题**，是 WorkBuddy 沙箱注入的 `NODE_OPTIONS=--require .../node-language-shim.cjs`（配 `CODEBUDDY_SAFE_DELETE_*`）被 `next dev` 及其子进程继承；Turbopack 清理 `.next/dev/server/chunks/*` 时撞上 safe-delete 的「单轮 50 条」守卫，抛 `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]` ⇒ `static-paths-worker` 子进程退出 ⇒ jest-worker（dev 里 `maxRetries: 1`）报「2 child process exceptions」。
- 验证：`env -u NODE_OPTIONS -u CODEBUDDY_SAFE_DELETE_ENABLED npx next dev -p 3000` 起服务后一切正常：`/zh` 200、`/zh/games` 200、`/zh/games/contra` 200（详情页语言条渲染出 中文/English）、`/api/games/contra/rom?lang=zh` 206。
- ⚠️ 以后 dev 只在**用户自己的终端**跑（`pnpm dev`），别在 agent 沙箱 shell 里起；非要在沙箱里起就 `env -u NODE_OPTIONS`。
