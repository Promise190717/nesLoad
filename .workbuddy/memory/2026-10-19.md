## 线上 PS1 几乎全部打不开：根因是 ROM 代理传不了大文件（2026-10-19 定位）

- 现象：`/zh/consoles/ps1` 的 460 款里基本都开不了。
- 复现（本机 Chrome 无头 + 线上真实 `/zh/play?id=`）：296MB 的 `disney-tarzan.chd` 到手只有 **7,900,864 字节** ⇒ `checkChdIntegrity` 判 `truncated` ⇒ `载入失败: IncompleteRomError`。小文件（25MB `captain-tsubasa.pbp`）能正常起核。
- 直接量 `/api/games/<id>/rom`：整包 GET 反复只给 **1–3MB**（`http=200`，chunked，无 `Content-Length`）；`Range: bytes=0-4999999` 直接 **503 `error code: 1102`**（Worker 超资源上限）；但 1/2/4/8/16MB 的单段 Range 全部完整、且 **4 路并行 8MB 分片 19s 走完 32MB**。
- 上游 `files.retrogamesnexus.com` 直连同一文件 **296MB/383MB 全量正常**（2.5–4MB/s）⇒ 问题不在上游、不在 R2、不在核心/格式（`pcsx_rearmed` wasm 里有 `bin|cue|img|mdf|pbp|toc|cbn|m3u|chd|iso|exe`，BIOS 可回落 HLE）。
- 数据形状：PS1 460 款 = zip 245 / chd 131 / 7z 57 / pbp 22 / bin 2 / iso 2 / cnd 1（`cnd` 是错扩展名），全部 `files:` 走上游代理；抽样 12 个 chd 结构自检全 `ok`，**不是坏盘**。
- 结论：Cloudflare Worker 单请求搬不动 100MB+（约 50–60s / 100MB 量级的天花板），PS1 盘天生 200–780MB ⇒ 必然挂。同一条路 65MB 的 NDS 能过（44s），111MB 的直接 1102。

## ⚠️ 目录页「带查询参数的链接」不能走软导航（2026-10-19 线上事故，已修）

- 现象：线上（已登录、`/zh/consoles/nds?lang=zh` 与 `?page=2`）点语种 tab / 翻页 / 机种筛选，**地址栏变了、列表和红色高亮纹丝不动**；本地 `next dev` 完全正常。
- 排查：中途问过用户，答复「地址变了内容没变 / 带 /zh 前缀、已登录」。用真实 Chrome（CDP 探针）压测线上：
  · 整页文档请求（curl + 直接导航）永远是**对的**（`aria-current`、页码、列表都对）；
  · 失败的是 `<Link>` 的**软导航**：RSC 200 回来了（`x-nextjs-rewritten-path: /zh/catalog/console/nds/lang%3Dzh`）但客户端不应用；
  · `/zh/games` 点「下一页」同样失败（`?page=2` 仍停在 `1 / 137`）⇒ 不是机种页独有；
  · 反例：在 `/zh/games?page=2` 上切**界面语言**（`/zh` → 无前缀）是好的 —— 因为 `[locale]` 这一层段变了，客户端整棵树替换；**只改查询参数**才会走到那条失败路径。
- 根因：`middleware.ts` 的 `catalogRewrite()` 把带 `q|console|lang|page` 的地址改写到 `/catalog/...`（换了一棵路由树，为了每种查询组合各自有一份 ISR 缓存）。整页请求无所谓，但软导航拿回的 flight 载荷 segment 对不上当前树 ⇒ 客户端只更新地址栏。
- 修法：新增 `components/CatalogLink.tsx`（渲染普通 `<a>`，整页跳转），把 games / console / developer / developers 四页的**筛选条与翻页**链接、`GamesSearchForm` 的「清除」全换过去；`GamesSearchForm` 提交改回**原生 GET 表单**（`onSubmit` 只把按钮切成「搜索中…」，不再 `preventDefault` + `router.push`），空的搜索框不挂 `name` 以免多一跳 307。
- 代价：这些点击变成整页文档请求（命中 R2 里的路由缓存，很快），换来线上行为正确；**静态缓存架构原样保留**。
- 否掉的替代方案：① 让页面直接读 `searchParams` ⇒ 路由变动态、ISR 全废，且 Workers 每次浏览付渲染 CPU；② 把 RSC 请求也改写到 `/catalog` ⇒ 载荷仍然对不上，症状只会换方向复发。
- 校验：`tsc --noEmit --incremental false` 只剩既有 4 条 open-next 缺依赖；改动的 6 个文件 eslint 0 条。**没有本地实测**（按用户要求）。

## 分片下载改「自适应档位」（`lib/http.ts` 第二次迭代）

用户看 Network 面板发现每次大小从几十 KB 到几千 KB 不等 —— 那是「固定 8 MiB + 失败对半切 + 重试」三层叠出来的。改成：

- 网格 `ROM_GRID_BYTES = 2 MiB`，档位按**格数**升降（4 格 8 MiB / 2 格 4 MiB / 1 格 2 MiB），`parts` 按格下标 —— 片大小可升降而拼装顺序不变。
- `ROM_DOWNGRADE_AFTER = 1`：一批切过就降一档（原来是硬试 8 MiB 4 次）；`ROM_UPGRADE_AFTER = 8` 干净 8 批才升回。
- `ROM_RETRY_FULL_BELOW = 4 MiB`：**大段只重试 1 次就切半**（切半比退避更有效），小块才用满 `ROM_SPAN_RETRIES = 3`。
- 段级再兜一层：一批彻底失败 → 歇 3 秒**原样重走一遍**（`worker` 里），第二遍内部照样重试/降档/切半。
- `spanBackoffMs` 封顶 2s → **5s**：实测 503 是**成片**来的（`41943040-50331647` 与 `50331648-58720255` 相邻段一起挂），是限流窗口，300ms 重撞没意义。
- `ROM_SPLIT_DEPTH` 一度被我改成 2 —— **错的**：8 MiB 段只切到 2 MiB 就到底了，比原来（切到 512 KiB）弱 4 倍，已改回 4。

自测：
- mock（`Response` + 固定种子模拟 503/截断）40 MiB：**逐字节一致**，7 个请求（理论 6）。
- 线上 92 MB pbp：65.5s 全量、头 `00504250`（PBP）✅；同日三次分别 167s / 79.8s / 65.5s，波动很大。
- 线上 296 MB chd：**连测三次都失败**（73% / 87% / 更低），失败点全是成片的 503。判断是我自己连续压测触发了**限流**（越测越差），不是逻辑问题 —— 但结论要写清：300 MB 级在这条路上仍然不稳，终极解仍是 R2。

## 街机 `/play` 无限刷新：HTML 被 CDN 钉了一年

- 现象（用户截图）：`(0, h.v) is not a function` + `Right-hand side of 'instanceof' is not an object`，页面自己一直刷新。`h.v` 是 `localCoreWasmUrl`，`UnsupportedRomError` 也 undefined ⇒ **新代码调到旧 chunk**。
- 量到：`/zh/play`、`/zh/room`、`/zh/privacy`、`/zh/terms` 全是 `s-maxage=31536000, stale-while-revalidate=2592000` + `x-nextjs-prerender: 1`（永久静态页）；而 `/_next/static/*` 是 `max-age=31536000, immutable`。
- 4f8263a 加了 `localCoreWasmUrl`，但线上 chunk 名还是 `0fe0plnjka4ry.js` / `0y0l5iwj4xp9f.js` 那批 —— **chunk 名不随内容变**，`immutable` 的前提不成立。旧 HTML 指向已替换的 chunk ⇒ Next 判定加载失败 ⇒ `location.reload()` ⇒ 还是旧 HTML ⇒ 死循环。
- 修：四个页面加 `export const dynamic = 'force-dynamic'`（HTML 每次生成）；`next.config.js` 新增 `/_next/static/:path*` → `public, max-age=0, must-revalidate`（每次 304 验证，内容没变几乎零成本）。
- ⚠️ **部署后必须 purge 一次 Cloudflare 缓存**：边缘上还躺着 `s-maxage=31536000` 的旧 HTML，不清就会继续返回旧页。
