## ROM 客户端复用缓存（`lib/rom-cache.ts`）

用户发现玩 PS1 时 `/api/games/<id>/rom?lang=en` 回 `private, no-store`，问是不是没设缓存。结论是设计如此：
`route.ts` 只在「响应体就是整个文件」时给 `public, max-age=604800`，而 `fetchRomWithProgress` 一律先发
`Range: bytes=0-8388607` —— ≤8 MiB 的卡带会被归一成 200 可缓存，>8 MiB（街机/GBA/NDS/PS1）每一片都是真分片，
只能 `private, no-store`（半截字节进缓存 = 所有人拿到坏 ROM 且静默失败）。

用户选了「客户端缓存」这条路：

- 新增 `lib/rom-cache.ts`：Cache Storage `nesload-roms-v1`，键 = ROM 接口地址本身（`?lang=` 天然分开）。
  元信息放响应头 `x-rom-cached-at` / `x-rom-cached-bytes`，不另建索引（CacheStorage 没有 TTL，只能自己记）。
  7 天 TTL 对齐服务端 `ROM_CACHE_SECONDS`；单份上限 512 MiB、总量 1 GiB，超了按最久没缓存的先删；
  写前用 `navigator.storage.estimate()` 先问配额，写失败一律静默（纯加速，不能影响开局）。
- `lib/http.ts` 的 `fetchRomWithProgress`：开头读缓存（命中直接 `onProgress(1)` 返回），三条成功路径
  （200 整包 / 单片装下 / 分片拼完）都在返回前 `void cacheRom(...)`。中途断开的半成品绝不入缓存。
- 两个 Scene（ConsoleScene / PlayScene）**零改动**：缓存挂在共用函数里，URL 自带 id + lang 就是键。
- ⚠️ `public/sw.js` 的 activate 是「名字不认识就删」，必须放行 `nesload-roms-` 前缀，否则换一版 SW 就把
  用户攒的 ROM 悄悄清空。VERSION 没升（新缓存此前不存在，没有旧副本要作废）。

只做了 `tsc --noEmit` + `eslint`，按用户要求没有实测。

**当天回滚**：用户说「算了 改回去吧」，上面这套已全部撤销（`lib/rom-cache.ts` 删除、`lib/http.ts`
与 `public/sw.js` 回到提交状态）。留档只为记住两条判据：① `> 8 MiB` 的 ROM 在服务端就是

## PS1 单局内存账（回答「跑一个 PS1 游戏 2.4GB 合理么」）

- 判据公式：**稳态 ≈ 2 × 解出来的盘 + 300–400 MB**（MEMFS 里一份 + `lastRomRef` 攥着重载用的那份
  File + 核心堆 + 浏览器基线）。`lib/emulator.ts` 的 `writeRomIntoFs` 用 `canOwn=true`，MEMFS 直接
  持有那块普通 JS 数组，**运行期不释放**。
- 被问的那盘 = `rival-schools-united-by-fate`（私立正义学园 disc1），ROM 是
  `rival-schools-united-by-fate-disc1.7z`，**实测 Range 得 278,431,342 B ≈ 265.5 MiB**（ps1 未进 R2，
  走上游代理，chunked 无 content-length，只能靠 `Content-Range` 问）。
- **7z 这条路才是 2.4GB 的来源**：`lib/unwrap.ts` 的 `extractSevenZip` 要 `file.arrayBuffer()` 整份进
  JS 堆 + postMessage 结构化克隆一份进 worker（EJS 那份 worker 没给 transfer list）+ asm.js 堆里同时
  装输入和输出条目 + `{t:2}` 再克隆回主线程 + `new File([bytes])` 又一份 —— 解压瞬间能到 1.5 GB 以上。
- 结论口径：**峰值**（载入那十几秒）2.4GB 属预期；**稳态**（玩几分钟后）对 500–700 MB 的盘应落在
  1.4–1.8 GB，还挂 2.4GB 就是中间产物没回收，值得查。验证用控制台那行
  `[nesload] 大文件直写：xxx（N 字节）` 拿到真实 N 再套公式。
- 未改任何代码。

## 线上实测：所有带动态段的路由都没缓存（`private, no-store`）

用户拿 `https://www.retrogamesonline.fun/zh/consoles/gba` 问「为什么 cache-control 不缓存」。实测（curl -I）：

- `x-opennext-cache: HIT` + `s-maxage=25171xx, stale-while-revalidate=2592000`：`/zh`、`/zh/games`、`/zh/consoles`、`/zh/developers` —— **只有 URL 里没有动态段的那几个**。
- `x-opennext: 1` + `private, no-cache, no-store, max-age=0, must-revalidate`：`/zh/consoles/gba`、`/consoles/gba`、`/zh/consoles/gba/page/2`、`/zh/consoles/gba/lang/zh`、`/zh/games/console/gba`、`/zh/developers/capcom`、`/zh/games/<slug>` —— **凡带 `[id]`/`[type]`/`[n]`/`[code]` 的全中**。

根因（未改代码）：这个头就是 Next `lib/cache-control.js` 的 `revalidate === 0` 分支。全项目 `generateStaticParams` 只有两处 —— `app/[locale]/layout.tsx`（返回 LOCALES）和 `app/[locale]/catalog/[kind]/[id]/[query]/page.tsx`（返回 `[]`）。子段没有 `generateStaticParams` ⇒ 路径不进 prerender manifest ⇒ Next 把路由当 `ƒ` 动态渲染 ⇒ 页面上的 `export const revalidate = 2592000` 是**死配置**，一个条目都不会写。

`docs/cloudflare-deployment.md:40-42`（「详情页默认预生成 24 款」「其余首次访问生成并缓存 30 天」）与线上不符，那段是重构前的口径。

另注：游戏详情页还有第二重原因 —— `app/[locale]/games/[id]/page.tsx` 用 `readViewer()` 读 cookie 出首屏评论登录态，**天生 dynamic**；就算补了 generateStaticParams 也不会回到 s-maxage，得把登录态挪到客户端才有解。机种页 / 机种筛选页 / 开发商页没有读 cookie，是纯「缺 generateStaticParams」。

**追问：点「返回」后页面内存不降。** 静态核对过释放链是完整的：`PlayScene` 卸载时
`abort()` → `lastRomRef.current = null` → `controller.exit()`（依次 detach 键盘桥、清
`instance`/`currentRom`/`ejs`、`pause()`、`exit({removeCanvas:false})`、
`releaseEmulatorRuntime` 关 audio/worker/GL、`releaseCanvas` 还原 canvas 上 Emscripten 挂的属性）
→ `netplay.leave()`。所以更可能是**浏览器不还页**（V8 不缩堆空间 / wasm 线性内存是 reservation /
Blob 存储延迟 GC），不是 JS 引用泄漏。判定法：同一款反复进出 3 次看是否单调上涨（真泄漏）
还是稳定在同一档（不还页）。仍未实测、未改代码。

### ⚠️ 上面那句「不是 JS 引用泄漏」是错的 —— 实测是真泄漏，已修

用户回「你自己测试」，于是用 headless Chrome + CDP 实测（本地 `next dev`，避开 CF 挑战；
`Runtime.getHeapUsage` 把 JS 堆和 **ArrayBuffer 后备存储**分开看，外加进程工作集）。

**泄漏量 = 一盘 ROM / 每次进出，线性叠加。** `dice-de-chocobo`（内层 bin 131,817,840 B）三轮进出，
每轮「进 → 玩 20s → 点返回 → 连做 5 遍 GC」后的 `backingStorageSize`：

| | 起点 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|---|
| ArrayBuffer 后备 (MB) | 5 | **136** | **265** | **394** |
| 进程工作集 (MB) | 672 | 870 | 1059 | 1257 |

增量恒为 +129 MB ≈ 那盘 bin。JS 堆 (`usedSize`) 全程 10–15 MB 不动 ⇒ 不是 JS 对象，就是 MEMFS
节点里那块 `Uint8Array`（`writeRomIntoFs` 用 `canOwn=true` 交进去的）被钉住了 —— Emscripten 实例
在 `exit()` 之后好几轮 GC 都没被回收。**与 `lastRomRef`、Blob、浏览器不还页都无关。**

**修法**（`lib/emulator.ts`，45 行）：`EmulatorController.exit()` 在 `exit()` 之前先
`dropContentFiles(fs)` —— 把 `CONTENT_DIRECTORY` 里的文件逐个 `unlink`，那块数组当场变垃圾。
两处调用点都接上了（`loadRom` 里的 `releaseResources` 与 `exit()` 的兜底分支）。

**修后实测（同款三轮）**：后备 5 → 10 → 13 → 17 MB，工作集 670 → 734 → 806 → 879 MB。盘那份彻底不累积。
**残留**：每启动一次仍有 ~70 MB（PS1）/ ~25 MB（NES `wwf-wrestlemania` 对照）的工作集不回，
JS 堆与后备都是平的 ⇒ 只剩核心 wasm 堆那一份（Module 仍被某个闭包攥着），量级小一个数量级，
未继续追（要定位得上 heap snapshot 的 retainer 路径）。

**踩过的坑**：① 判「开局」不能看 canvas —— PlayScene 的显示区本来就是 canvas，会误判成已开跑；
要么等控制台 `[nesload] 大文件直写`（>32 MiB 才打），要么等页面不再显示「正在下载」。
② 直接打线上会被 Cloudflare 挑战卡住（`Click to reveal…`），本地 dev 快一个数量级（60 MB 约 60s）。
③ 探针里 `await send()` 没有超时，页面 HMR 重载后 CDP 断开就会永久 hang。探针全在
`%TEMP%\nesload-memprobe`，验完已删；`tsc --noEmit --incremental false` 与 `eslint lib/emulator.ts` 均干净。



### 补：载入途中离开的窗口（同日，回答「切到任何页面都会清吗」时发现）

`dropContentFiles` 只在 `exit()` 拿到 `this.instance` 时才跑，而 `this.instance` / `this.releaseResources`
**只在 `Nostalgist.launch` resolve 之后**（`loadRom` 尾部）才赋值。于是「载入中 → 点返回 / 切页」
这条路上 `exit()` 是空转，而 launch 不会被取消，它照样把实例建出来 —— 建完再没人认识它，
整盘 ROM 连同核心一起钉住。`/play` 原本靠调用方一句 `if (aborted) await controller.exit()`
（PlayScene:729）兜住了；`/room` 的 `loadRom` 调用点没有这层检查，是真空洞。

改法（`lib/emulator.ts`）：控制器加 `launching` / `exitRequested` 两个字段。`exit()` 在
`!instance` 分支里若 `launching` 就置 `exitRequested = true`；`loadRom` 在 `Nostalgist.launch`
前 `launching = true; exitRequested = false`，`finally` 里 `launching = false`，launch 落地
拿到 `nostalgist` 后若 `exitRequested` 则当场 `await this.exit()` 并 return（跳过 `currentRom` 赋值）。
`/room` 那边随之 `controller.rom` 为 null，正好回到「没插卡」。

判定「还有没有别的不清的路」的口诀：**只要离开时能进到 `exit()` 且 instance 非 null 就没问题**；
`instance` 为 null 的只有两种 —— 从没启动过（没东西可清）、启动未落地（现在靠这套标记兜）。
整页刷新 / 关标签页不用管，渲染进程直接回收。tsc 与 eslint 均干净，未实测。

### 评估：把「进入/离开游戏」改成硬跳（`<a>` / `location.href`）能不能绕开这个泄漏

**进入侧改硬跳等于白改** —— 进 `/play` 之前那个 document 里没有实例（详情页），残留来自上一次离开，
已经由 `exit()` 清掉。要硬跳只能跳「离开」那一侧，而 `PlayBackLink` 现在是 `router.back()/push()`
（`components/PlayBackLink.tsx:45`），详情页入口是 `<Link>`（`GameLanguageActions.tsx:146`）。

硬跳**确实**能绕过去，而且比 `dropContentFiles` 更彻底：document 一销毁，MEMFS 那块数组、wasm 实例、
Emscripten 的注册表一起消失，连残留那 ~70 MB 也不用等 GC。但代价三条：
① 返回是最高频操作，详情页整页重渲染比软导航慢几百 ms；且全站目录链接都是软导航（刻意设计），破例不一致。
② history 语义变了，`router.back()` 得换成 `location.replace(href)`，`history.length` 那套判断失效。
③ `netplay.leave()` 被跳过 —— 联机退房靠显式 `host-left` 消息（`lib/netplay.ts:745`），不是纯连接断开感知，
对端要等超时。
**决定性的一条**：根因没修。`/room` 拖新 ROM、`/play` 读档重插、联机 `remountRom` 都是同一个 document
内的重新开局，硬跳一点管不到，那些路径照样泄漏。结论：不换；真要清那 70 MB，该做的是在
`releaseEmulatorRuntime` 里断掉 Module 闭包引用，而不是刷页面。

### /play 的 ROM 载入：内存三处、速度一次实测（房间页下线后第一次动这条链）

链路只有一条：`fetchRomWithProgress`（分片 Range）→ `new File` → `unwrapRom`（zip 用
DecompressionStream 流式解，7z 走 worker）→ `controller.loadRom` → 超 32 MiB 的走
`writeRomIntoFs`（`new Uint8Array(size)` + `canOwn=true`，MEMFS 直接持有）。

**改了三处（都在 7z 那条路，PS1 的大盘全走它）：**
1. 主线程 → worker **加 transfer list**：`worker.postMessage(bytes, [buffer])`。原来不带，
   整包在结构化克隆里又复制一份（`rival-schools` 265 MB ⇒ 白占 265 MB）。
   注意方向：worker **回传**那条已经由 2026-10-19 的补丁移交了，两边别搞混。
2. `extractSevenZip` / `unwrapRom` 收 `AbortSignal`：取消时当场 `worker.terminate()`，
   不再让它解完几十秒。`unwrapRom` 对取消**不吞**（和「解不开吞掉返回 null」区分），
   PlayScene 把 `ac.signal` 传进去了。
3. 新增 `takeAsFile()`：7z 条目建完 File 就把 `entry.data` 换成空数组。
   否则 cue + bin 套装在「建伴生文件」那一刻同时握着两份整盘。

**速度实测（本机 → 线上 `/api/games/<ps1>/rom`，取中间 12 MiB）：**
`1×2MiB` 0.20 MB/s、`3×8MiB` 0.57 MB/s、`6×8MiB` 0.34 MB/s。
但本机到 Cloudflare 的基线也一样慢（8 MB 直连 120 s 跑不完），**测出来的绝对值不可信**，
所以**没动** `ROM_CHUNK_CONCURRENCY` / `ROM_GRID_BYTES`。3 路在当前实现里是合理值。

**还剩的两处大改（没做，等用户点头）：**
- 让 7z 解出来的大盘**直接进 MEMFS**（不建 File）：省掉「Blob 一份 + MEMFS 一份」里的
  第一份，约等于一整盘（500–700 MB）。代价是要给 `UnwrappedRom` 加字节通道、并把
  `detectConsole` 的输入从 Blob 改成「头 + 名字」，`console` 字段要跟着补齐。
- 换 wasm 版 7z（EJS 给的是 asm.js，64 MB 包在 Node 上 14.6 s）：解压快 5–10 倍，
  但要 vendored 一份新产物 + 重写 `extractSevenZip` 的协议。

### 用库里的机种替掉 sniff，7z 解出来直接进 MEMFS（房间页下线后才成立）

`game.consoleType` 与那条 ROM 是同一条记录 ⇒ 权威来源本来就在手上。

1. **`loadRom` 加第 6 参 `consoleHint`**：优先级 `unwrapped.console` → `consoleHint` →
   `detectConsole`。`PlayScene` 传 `game?.consoleType ?? null`。嗅探现在只在后台导入
   （`AdminGames`，它用新导出的 `romFileOf()` 现建 File）和没带提示的调用方用。
   风险已核：DB 的机种来自上游按机种分页，和 ROM 同源；`preloadCoreWasm` 本来就已经
   在用 `game.consoleType` 选核心了。
2. **`UnwrappedRom` 改形**：`file: File` → `main: UnwrappedEntry`（`{name,size,file|null,bytes|null}`），
   `companions: File[]` → `UnwrappedEntry[]`。7z 那条 `takeAsFile()` 换成 `takeBytes()`
   （**不再建 File**，也不再断 `entry.data` 的引用 —— 交出去的就是那块数组本身）；
   zip 那条用 `takeBlob()`（`new File([blob])` 对 Blob 只加引用，不搬字节）。
3. **`writeRomIntoFs` 收 `RomContent`**：有 `bytes` 就直接 `createDataFile(..., canOwn=true)`
   （核过核心 js 的 `MEMFS.write`：canOwn 时 `node.contents = buffer.subarray(0,len)`，
   一次复制都没有）；没有才走原来的 8 MiB Blob 切片。`StagedRom` 多一个 `size` 字段打日志。
4. **`checkChdIntegrity` 改成 `ChdSource`**（`{size, read(start,end)}`）+ 两个构造函数，
   免得为了自检把几百 MB 的 `Uint8Array` 包成 Blob。判据一行没改。

7z 大盘的峰值从「数组 + File 里的 Blob 副本 + MEMFS 数组」三份降到**一份**
（265 MB 的 7z 解出 ~600 MB 的盘：约 1.8 GB → 约 865 MB，含 `lastRomRef` 里那份压缩包）。
`tsc --noEmit --incremental false` 干净；eslint 对 6 个改动文件只剩既有的
`react-hooks/set-state-in-effect`（全在 ConsoleScene，行号都不是我碰的）+ PlayScene 的 `<img>`。
**未实测**（按用户规矩不主动跑浏览器）。

### 第二处大改：7z 换成 wasm（2026-10-21 下午）

`public/compression/` 里那份 EmulatorJS 的 **asm.js** `extract7z.js`（280 KB，被我们打
过 transfer 补丁）整个删掉，换成 7-Zip 24.09 官方源码编的 wasm：
`7zz.wasm`(1.65 MB) + `7zz.umd.js`(83 KB)，来自 npm `7z-wasm@1.2.0`，许可证两份 txt
一起放进去了。新 worker 是**手写**的 `extract7z-wasm.js`（不再是 vendored 产物，
补丁会丢那个坑随之消失）。

实测（同一台机器、同一个 PS1 包 `rival-schools` 265 MB → 692 MB bin，
headless Chrome 直接跑两个 worker，同一份包）：

| | asm.js（旧，sha1 `a0247…`） | wasm（新） |
|---|---|---|
| 解压 | **42.6 s** | **19.0 s**（纯解压 17 s） |
| 主线程 ArrayBuffer 峰值 | 692.0 MB | 692.0 MB（看不出差别） |

⚠️ **别再说「快 5–10 倍」**：那是拿 2026-10-15 那个 NDS 小包（64 MB 包 → 128 MB，
14.6 s）按体积外推出来的，实际不对。同一个 PS1 包实测就是 **2.2 倍**。

- **输入侧**是这次顺带的第二个大头：emscripten 的 `WORKERFS` 能把 `Blob` 挂成只读文件，
  读的时候才 `FileReaderSync` 取段（`Blob.slice` 是引用）。所以 `lib/unwrap.ts` 的
  `extractSevenZip` 现在直接 `worker.postMessage(file)`，不再 `arrayBuffer()`。
  ⚠️ WORKERFS 的 mount 里写着 `assert(ENVIRONMENT_IS_WORKER)`，必须在 worker 里挂。
- **输出侧不 slice**：MEMFS 几何扩容（≥1 MiB 后每跳 1.125 倍），692 MB 的文件实际占
  702.9 MB；`FS.readFile` 返回的是「精确长度、共享整个 buffer」的视图，直接 transfer 出去，
  主线程按 `.length` 用（`createDataFile(canOwn)` / `new File([view])` 都是按 view 长度），
  省掉一整盘复制。**改成精确扩容反而更差**：7-Zip 是边写边扩不是先 truncate，
  同一个包 16.2 s → 74.1 s、内存 3.8 GB，已否决。
- **进度**从 stdout 逐字符抠（7z 用 `\b` 重画同一行，emscripten 的 `print` 是行缓冲永远
  等不到换行）；协议加了 `{t:9}`，因为 worker 里 async 流程的未捕获 rejection 不触发
  `onerror`，不加就静默挂住。
- `next.config.js` 补了一条 `7zz.wasm` 的 `Content-Type: application/wasm`（精确匹配）。
- 验证：headless Chrome 起静态服务跑最小页面，小包 362 files / 4.71 MB / 0.4 s，
  大包 2 files / 692.01 MB / 19.0 s，进度 0→90 正常，transfer 正常。
- 缓存：`/compression/*` 仍是 24 h，**换文件后必须 purge CDN**（文件名不带 hash）。

### 功能实测（2026-10-21 下午，headless Chrome + dev server 3100）

`/zh/play?id=rival-schools-united-by-fate&mode=solo`，两轮完整进出：

| | round 1 | round 2 |
|---|---|---|
| 载入峰值 ArrayBuffer | 701.6 MB | 701.6 MB |
| 点「←返回」→「离开并返回」12 秒后 | **10.1 MB** | **5.3 MB** |

- 载入拆解：下载 265 MB 约 48 s（34 个 8 MiB Range 分片）+ **解压约 17 s** + 核心启动几秒。
- **返回后内存是清掉的，两轮不叠加**（第二轮的 baseline 就是上一轮残留的十几 MB）。
  用户看到的「tab 内存没下降」不是泄漏 —— `Runtime.getHeapUsage` 的 `backingStorageSize`
  从 701.6 掉到 10.1 只用了 12 秒（每轮都手动触发过 GC）。真实浏览器任务管理器看的是
  进程 RSS，V8 释放 ArrayBuffer 后未必要立刻 `madvise` 还给 OS；让用户按一次
  DevTools → Memory 的垃圾桶就能分辨。
- ⚠️ `Runtime.getHeapUsage` **只统计主线程**，worker 里的内存看不到。所以「输入侧省掉
  265 MB」只能从代码推（旧版 `arrayBuffer()` 再写进 MEMFS，新版 WORKERFS 挂 Blob），
  这个指标证明不了，别拿它当证据。
- 测「返回」必须点确认弹窗那颗「离开并返回」（`PlayBackLink` 在游戏运行中会先拦一道）；
  直接 `history.back()` 在这个 SPA 里不一定出得去（`Page.navigate` 进来时 history 只有一条）。
